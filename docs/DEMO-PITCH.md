## الشرائح — ست شرائح فقط
1. المشكلة: اكتشاف الأنشطة المناسبة، ووصول المشاريع المحلية.
2. الحل: من طلب عربي طبيعي إلى أنشطة مناسبة من بيانات محددة.
3. Live Demo: اتركوا الشريحة واعرضوا التطبيق.
4. AI والبيانات: pipeline مختصر + مقارنة ترتيب مقاسة.
5. الأثر ونموذج العمل: فرضية القيمة وكيف سنقيسها.
6. ما يعمل الآن، القيود، وخطة 30 يومًا.

## Live Demo checklist
- متصفح/ملف جلسة للشركة وآخر للزائر؛ لا تبديل تسجيل دخول طويل.
- بيانات الإدخال في ملف محلي جاهزة للصق؛ لا تعرضوا كلمات المرور.
- إعلان جديد واضح أنه Synthetic، ومعلوماته تجعل أهليته متوقعة دون فرض ترتيبه.
- نفس نسخة البيانات عند مقارنة التخصيص؛ اعزلوا تجربة الإضافة عن تجربة تبديل التفضيلات.
- عند فشل AI: اعرضوا رسالة fallback واشرحوها؛ استخدموا التسجيل لإثبات التشغيل السابق إن لزم.
- نسخة 90 ثانية: عرض جاهز للشركة → إدخال الزائر → النتائج والأسباب → مقارنة ترتيب واحدة.
- أي فيديو احتياطي يُعلن صراحة أنه تسجيل.

## أسئلة صعبة وإجابات صادقة
| الحكم/السؤال | الإجابة |
| --- | --- |
| AI: أين الذكاء الاصطناعي فعليًا؟ | في استخراج الطلب وفي semantic_score الذي يغير ترتيب المرشحين. نعرض مقارنة مع baseline بنفس البيانات والقيود. |
| AI: لماذا لا تكفي filters؟ | تكفي للميزانية والسعة؛ لكنها لا تمثل جيدًا وصفًا مثل يوم هادئ وتجربة أصيلة. نختبر إضافة الترتيب الدلالي ولا نفترض أنه يتفوق دائمًا. |
| AI: هل النظام مجرد prompt؟ | الـLLM جزء من pipeline يتضمن عقودًا وبيانات وصلاحيات وفلاتر واختبارات. لا ندّعي ابتكار نموذج أساس جديد. |
| AI: لماذا لم تستخدموا embeddings؟ | 24 سجلًا يمكن تقييمها مباشرة؛ سنختبر retrieval دلاليًا عند نمو البيانات، مع بقاء التحقق الحتمي. |
| AI: كيف تمنعون الهلوسة؟ | حصر المرشحين في IDs من DB، والتحقق من المجموعة الكاملة، وإعادة جلب الحقائق، وقوالب أسباب مبنية على حقول مسموحة. لا ندّعي انعدام جميع أخطاء فهم اللغة. |
| AI: ماذا لو كتب النشاط ignore instructions؟ | الوصف يعامل كبيانات؛ لا يستطيع تجاوز الفلاتر أو إدخال ID جديد. نختبر هذا المثال صراحة. |
| AI: هل تختلف النتائج لأن filters تغيرت فقط؟ | نعرض اختبارًا بقيود ثابتة، وablation بأنشطة متشابهة tags مختلفة الأوصاف، ثم نقارن D وS وF. |
| AI: ما دقتكم؟ | لا توجد لدينا دقة عامة مثبتة. نعرض عدد الحالات، انتهاكات القيود، ونتائج تقييم صغيرة محددة وحدودها. |
| AI: لماذا 65/35؟ | اختيار أولي قابل للاختبار يُظهر دور AI ويحافظ على baseline؛ ليس وزنًا أمثل مثبتًا. |
| AI: لماذا يظهر نشاط جديد بلا تدريب؟ | نسترجع أحدث السجلات في كل طلب؛ تغيرت البيانات المرشحة، ولم تتغير أوزان نموذج الأساس. |
| AI: هل كل نشاط جديد يظهر أولًا؟ | لا. يصبح مؤهلًا للتقييم فقط؛ ترتيبه يعتمد على الشروط والملاءمة. |
| تقني: ماذا عند انقطاع الخدمة؟ | Timeout مضبوط، ثم rules_fallback معلن؛ وإذا فشل استخراج قيود مهمة نطلب تعبئة الحقول بدل التخمين. |
| تقني: هل يمكن لشركة تعديل أخرى؟ | نتحقق من الهوية والملكية في الخادم وRLS، ونختبر حسابين وعلى Supabase مباشرة. |
| مجال: من أين البيانات؟ | صفحات رسمية لحقائق الأماكن، وبيانات جهة مقدمة للخدمة عند توفرها بإذن، وعروض افتراضية موسومة. لكل منها مصدر وحالة تحقق منفصلان. |
| مجال: هل الأسعار والتوافر محدثان؟ | الأسعار تحمل حالة وتاريخًا، وتصبح غير مؤكدة عند انتهاء صلاحيتها. لا يوجد تكامل توافر حي، لذلك نطلب التأكيد من الجهة. |
| مجال: لماذا ليس Google Maps أو TripAdvisor؟ | لا نستبدلهما. نختبر تجربة طلب عربي بميزانية المجموعة وربطها بعروض محلية منظمة؛ ويمكن استخدامهما لاحقًا للملاحة والتحقق الإضافي. |
| مجال: هل كلمة family تعني نشاطًا آمنًا للأطفال؟ | لا. نستخدم التصريح المنظم فقط، ونوضح أنه تصريح الجهة؛ الأعمار والمتطلبات والسلامة تحتاج معلومات مؤكدة قبل الإطلاق الفعلي. |
| أعمال: لماذا يستخدمه مشروع صغير؟ | فرضية القيمة وصول أكثر صلة بدل مجرد الظهور؛ سنقيس عدد الاتصالات المؤهلة لكل عرض ووقت إنشاء القائمة. |
| أعمال: كيف ستجلبون الطرفين؟ | تجربة صغيرة في منطقة واحدة مع خمس جهات بموافقتها، وروابط/QR لدى المشاركين وحملة محتوى محلي؛ هذه خطة وليست شراكات قائمة. |
| أعمال: كيف ستربحون؟ | إدراج أساسي وزوار مجانًا، ثم اختبار اشتراك لأدوات الشركات أو leads بموافقة وتعريف واضح؛ عمولة الحجز مؤجلة حتى يوجد حجز فعلي. |
| أعمال: هل الدفع يؤثر على توصياتكم؟ | الترتيب العضوي يفصل عن إعلان مدفوع موسوم؛ لا بيع لتجاوز القيود الصارمة. |
| أعمال: ما الكلفة؟ | افتراض 3500 input و900 output يعطي نحو $0.00284 للطلب بالنموذج المختار؛ نقيس التكلفة الحقيقية من usage. الاستضافة والمقاعد منفصلة. |
| أعمال: هل أثبتم أثرًا اقتصاديًا؟ | لا. سنقيس وصولًا واتصالات أولًا، ثم نتائج تؤكدها الشركات بموافقتها. النقر ليس حجزًا ولا زيادة دخل. |
| أعمال: كيف ستتوسعون؟ | توحيد بيانات الجهات والتحقق والتحديث أولًا، ثم فهرسة/semantic retrieval عند نمو الكتالوج، مع مراقبة تكلفة وجودة كل مرحلة. |
| عام: ما المنفذ وما المحاكى؟ | نعرض قائمة دقيقة من README النهائي: ما يعمل حيًا، العروض Synthetic، والميزات غير المنفذة. لا نعرض الخطة كأنها منتج مكتمل. |

## فرضيات business قابلة للاختبار
- أول 30 يومًا: 5 جهات متطوعة في نطاق صغير، 30 عرضًا بإذن، و20 جلسة استخدام اختبارية بموافقة أصحابها. أرقام أهداف وليست نتائج.
- مقاييس: نجاح العثور على نشاط، وقت الوصول لخيار، نسبة النتائج خارج المواقع الأكثر ظهورًا في عينتنا، نقرات تواصل مؤهلة، ونسبة leads تؤكدها الجهات.
- لا نستنتج أثرًا سببيًا أو إنفاقًا محليًا إضافيًا من النقرات. نحتاج baseline وفترة متابعة ومقارنة أو تجربة قبل هذا الادعاء.
- أسعار الاشتراك ليست مثبتة. اختبروا الاستعداد للدفع بالمقابلات قبل تسمية سعر نهائي.
- مثال تكلفة تشغيل مدفوعة صغيرة: Vercel Pro يبدأ $20 شهريًا بمقعد نشر واحد، Supabase Pro $25 شهريًا، أي أساس نحو $45 قبل API والاستخدام الإضافي والضرائب والمقاعد. 10000 طلب وفق الفرضية أعلاه تضيف نحو $28.40. ليست هذه فاتورة مضمونة.
